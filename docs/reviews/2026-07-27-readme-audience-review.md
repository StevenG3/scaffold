## 验收准则（本次审阅唯一 Spec）

用户明确要求 README 满足：

1. **说明项目的目的**
2. **说明项目的用法**
3. **不用说明项目的开发方式**

本记录只依据上述三条评判；不把「设计可追溯」「流程完备」「审阅链完整」当作 README 的加分项。

## 总判

| 准则 | 判定 | 一句话 |
| --- | --- | --- |
| 1. 目的 | **部分满足** | 开头与「背景」说明了为何存在，但目的叙述被仓库维护元叙述稀释 |

## Spec Findings

### [P2] 用法不是 README 的主路径

位置：`README.md`「快速验证」及全文结构

现状：

- 使用者真正需要的入口命令（`harness.py init --target …`、随后 bootstrap、日常 `validate` / `adapt`）挤在文末「快速验证」一段里。
- 同一段还混入**生产者侧**验证：`unittest`、校验分发包契约——这是维护本仓库的人做的事，不是把 Harness 接到业务项目的人的主路径。
- 缺少清晰的用法骨架，例如：前置条件（Python 3.9+）→ 安装/实例化到目标项目 → 定制（bootstrap）→ 日常校验与投影刷新 → 在哪里读消费者文档（如目标项目内 `.harness/README.md`）。

要求：

1. 增加独立的 **「用法」**（或「快速开始」）章节，并放在目的之后、尽早出现。
2. 用法章只写**消费者路径**；仓库自测命令如需保留，放到文末极短的「维护者附注」或链到 `docs/`，不得与用法并列抢戏。
3. 用有序列举写清最少步骤与关键命令；一句说明 `init` / `adapt` / `validate` 各自何时用。

### [P2] README 大量说明开发方式与过程资产

位置：`README.md`「本仓库做什么」「状态」「设计与决策」及审阅列表

违反准则 3 的具体内容包括但不限于：

- 「将设计参考与演进决策留在仓库内」「发现一次 Agent 错误 → 工程化消除同类错误」——这是工程方法，不是产品用法。
- 「状态」整段以交付清单 + **不变式闭包设计法** + **v2 规划准入门槛** 为主，读者学到的是「项目怎么演进」，不是「我怎么用」。
- 「设计与决策」枚举设计规格、ADR、**实施计划**与多份**审阅记录**——典型生产者/审阅者导航，不应作为 README 主体。

要求：

1. 从 README 正文移除或大幅压缩开发方式、流程方法论、实施计划与审阅链；需要保留时改为「详细设计见 `docs/design/`」一条链接即可。
2. 「状态」若保留，只保留**对使用者有意义的产品状态**（例如：当前稳定能力是 v1：`init` / `adapt` / `validate` + 平台投影），不写流程是否生效、规划如何定型。
3. 「本仓库做什么」改为用户价值表述（接到项目后能得到什么），删除 Git 版本化管理、可追溯审阅之类的维护者叙事。

### [P3] 目的可读，但不够「产品第一句」

位置：`README.md` 开篇与「背景」

目的相关句子已经存在（通用 Harness、约束/反馈/编排、稳定可审计交付）。问题在于：

- 第一句是「本仓库用于沉淀并维护…」，主语是仓库维护，不是用户问题。
- 「背景」偏范式史（Prompt → Context → Harness），对「我为什么要 `init` 到我的项目」帮助有限。

建议（非阻塞，但强烈建议与 P2 一并改）：

1. 开篇用 2–4 句回答：解决什么问题、给谁用、交付物是什么（可复制的 `.harness/` + CLI）。
2. 背景可缩为一段或不放在 README，细节留给 `docs/reference/`。

## Standards Findings

### [P3] 信息架构不利于「目的 → 用法」扫读

在不增加新规范文件的前提下，仅就文档可读性：当前章节顺序为背景 → 仓库职责 → 参考资料 → 许可 → 状态 → 设计与决策 → 快速验证。使用者要读到用法需穿过大量过程信息。修订时应保证：**目的 → 用法 →（可选）许可/状态**，过程文档一律下沉。

未发现与本次三条准则无关、且必须阻塞的排版/链接类硬伤；许可与第三方摘要声明本身合理，可保留，但建议不要插在「目的」和「用法」之间过长。

```markdown
- 设计与 ADR → docs/design、docs/adr
- 不要在此展开实施计划与审阅轮次
```
