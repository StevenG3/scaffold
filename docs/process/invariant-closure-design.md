# 不变式闭包设计法 — 设计与整改的强制流程

- 状态：Proposed（v2 及后续所有设计适用；由 v1 交付复盘产出）
- 依据：[Harness v1 实现审阅（九轮全记录）](../reviews/2026-07-23-harness-v1-implementation-review.md)

## 1. 为什么需要这份流程

Harness v1 经历 8 个计划任务与 8 轮外部整改。复盘数据：

- 初始 8 个任务（实施计划含完整代码与测试）**一轮过审，几乎零返工**。
- 8 轮整改共约 28 个 Critical/Important，其中 **约 21 个是 3 个不变式的重复实例**：
  1. **信封全覆盖**：参数解析后的任何运行时故障不得逃逸为裸 `INTERNAL_ERROR`；
  2. **字节与进度真相**：受管区间外用户字节逐字节不变，报告的进度等于磁盘事实；
  3. **出口编码全域合法**：所有终端出口对任意输入产出严格合法、可无损往返的 UTF-8。

根因不是实现方执行力（实现方对明确要求的执行精度极高），而是**方法不对称**：
审阅方用全称命题检查（「∀ 边界都必须…」，逐轮做相邻缝隙探测），设计方却按
存在命题交付契约（逐阶段点名），实现方按 finding 逐点修补。一个全称命题
不可能靠逐点修补收敛——差额就是 8 轮返工。转折点是 R5 改为「统一异常分类、
修类不修实例」，随后各轮新发现迅速衰减至合入。

## 2. 设计交付要求（对设计方）

任何新设计（含对既有契约的修订）必须包含：

### 2.1 全称不变式

用「对所有 X 均成立」的形式陈述核心承诺，而不是列举已知场景。示例：

> post-parse 生命周期内，∀ 文件系统与编码操作的故障 → 稳定错误码 + 按
> `--format` 渲染的 envelope。

### 2.2 闭包枚举表

为每条不变式附一张**可机械核对**的表：实现将发生的每一个操作点
（syscall / 读取 / 写入 / 解析 / 规范化 / 关闭 / 编码出口）×
异常类别 × 错误码 × 退出码 × 测试义务。表是设计交付物的一部分，
实现与测试逐行对齐；表外新增操作点必须先回设计补行。

### 2.3 对抗输入域声明

显式声明每条不变式面对的输入全集，至少包含（按 v1 实战沉淀）：

- **文件系统节点**：普通文件、目录、symlink（目标/父目录/悬空/自环）、FIFO、设备、socket；
- **字节域**：CRLF、无末尾换行、空文件、非 ASCII、控制字符（C0/DEL/NEL/U+2028/U+2029）、
  代理字符（U+D800–DFFF，来源含 argv、文件名、异常消息）、字面转义序列与真实字符的碰撞；
- **部分失败**：短写、零进展、写中异常、替换异常、close 故障（含 close-before-consume）、
  检查-使用竞态；
- **语义冲突**：同一字段在不同条款中的措辞差异（如「本次写入」vs「当前有效」）必须裁定唯一语义。

### 2.4 兼容性承诺的精确边界

凡承诺「与既有行为逐字节一致」，必须写明该承诺覆盖的输入子集
（v1 教训：对本就产出非法字节的输入不存在可保护的兼容性）。

## 3. 整改交付要求（对实现方）

- **修类不修实例**：每个 finding 定位其所属不变式，交付**同类缝隙自查表**
  （该不变式的全部实例点 × 逐点核验状态），随修复一并提交报告；
- **红测先行**：回归测试必须先在被退回 HEAD 上真实见红；禁止恒真断言、
  禁止以 mock-only 探针替代真实路径/真实字节；
- **探针主动扩展**：每修一个探针，为同不变式补至少一个相邻探针，
  不等审阅方来探；
- **契约留白上报**：实现中遇到设计未定义的输入域，停止并上报设计方裁定，
  不按直觉处理。

## 4. 审阅前自检（对协调方）

交外部审阅前，内部复审必须完成一次**全表扫描**：按 2.2 的闭包枚举表逐行
核对实现与测试，产出扫描表而非「已检查」的断言。扫描表随交付证据一并提供。

## 5. 角色边界（v1 实战确认有效，保持）

- 设计方：拥有契约与裁决权；契约修订独立成 docs 提交，先于实现；
- 实现方：设计修订（获授权时）、实现、测试、提交；不修改审阅记录、不自评通过、不合并；
- 审阅方：独立复现、独立裁定、唯一的合入决定者；结论只绑定精确 HEAD。
