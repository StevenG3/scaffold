# Harness v2 规划草案 — 分层模板体系

- 状态：Draft（规划阶段；定型前置条件见 §2）
- 起草日期：2026-07-24
- 前置版本：[Harness v1 设计规格](harness-v1.md)（已交付合入）
- 适用流程：[不变式闭包设计法](../process/invariant-closure-design.md)（本设计为首个强制适用对象）

## 1. 定位

路线图 A（接入体验，已交付）→ **B（分层模板，本规划）** → C（演进同步）。

v2 要解决的问题：v1 的模板是单层通用体。真实项目需要的 Harness 资产大量与
**技术栈**相关（Java 的分层规范、TS 的构建门禁、Python 的测试约定……），
目前只能全部塞进项目层由 bootstrap 逐项生成。分层的目标是让
「通用层（流程/Change 管理）+ 技术栈层（可复用的栈专属 Rules/Skills）+
项目层（业务知识）」可组合拼装，栈层资产得以跨项目复用。

## 2. 定型前置条件（诚实声明）

v1 设计（§1）明文：分层「依赖 v1 的真实接入反馈」。当前接入项目数为 0。
本文档在反馈到位前**停留在 Draft**，只固化方向、候选与决策清单，不固化
合并语义——过早固化正是 v0 头脑风暴否决过的路线。

定型所需的最小反馈集（收集方式见 §6）：

- ≥2 个不同技术栈的真实项目完成 v1 接入并跑通 bootstrap；
- 每个项目 bootstrap 产出的项目层资产清单（哪些内容其实是栈级可复用的）；
- 定制过程中用户实际推翻/改写模板内容的记录（层边界的真实证据）。

## 3. 核心决策清单（候选与初步倾向）

### D1 层的物理形态

- A. **单包多层目录**：`.harness/` 内 `layers/common|stack-*|project/`，Manifest 声明启用层——分发仍是一个目录，`init --stack` 选层。（初步倾向：与 v1 自包含原则一致）
- B. 多包组合：栈层独立仓库/包，init 时下载拼装。（违反 v1 无网络非目标，排除出 v2）
- C. 生成式扁平化：分层只存在于模板仓库，init 时按选择烘焙成无层结构落地。（消费端最简单，但破坏 v3 升级锚点的层对应关系）

### D2 层合并语义

- A. **文件级覆盖 + Manifest 合并**：同路径文件按 project > stack > common 覆盖，Manifest components 做集合合并、id 冲突报错。（机械可校验，倾向）
- B. 区块级合并：文件内受管块粒度合并。（复用 v1 受管块引擎，但复杂度高，留待反馈证明必要性）

### D3 栈层的首批范围

由反馈决定，不预设。候选：接入项目实际所属的前两个栈。栈层内容本身
遵循 v1 规则约束（不含业务专属内容）。

### D4 校验器扩展

Schema v3（严格超集策略延续）：`layers` 声明、层内 Manifest 片段、合并结果
的确定性校验。`validate.py` 契约演进遵循 v1 §7.4 例外裁决的先例流程。

## 4. 不变式草案（定稿时按流程 §2.2 附闭包枚举表）

- **I1 合并确定性**：∀ 层组合，合并结果由（层集合，层内容）唯一决定——
  逐字节可重现，与合并执行顺序、平台无关。
- **I2 层来源可追溯**：∀ 合并产物文件，可机械回答「来自哪一层、被谁覆盖」；
  这是 v3 升级回流的锚点前提。
- **I3 组合封闭**：∀ 合法层组合的产物，通过 v1 全部既有契约校验
  （分层对下游不可见：投影、bootstrap、Change 管理无需感知层）。
- **I4 冲突显式**：∀ 未定义的同 id/同路径冲突，稳定错误码拒绝，
  不静默取先/取后。

对抗输入域（定稿时展开）：层内 symlink/路径逃逸（沿 v1 §8.3）、跨层同名
不同 kind、循环/缺失层引用、部分层损坏时的失败原子性、层清单的编码边界。

## 5. 分阶段交付设想

1. **B0（可立即做）**：v1 接入观察工具化——bootstrap Skill 增加「定制记录」
  产出（哪些内容被改、为何改），作为层边界的证据采集器；不改契约。
2. **B1**：D1/D2 定型（需 §2 反馈），Schema v3 设计 + ADR-0003，含闭包枚举表。
3. **B2**：合并引擎 + 校验器扩展 + 首个栈层内容，垂直切片交付。
4. **B3**：bootstrap 与分层协同（侦察结果建议启用哪个栈层）。

## 6. 近期行动（不依赖反馈、可并行）

- 将 scaffold 自身或维护者的真实项目作为第一批接入对象，跑通
  init → bootstrap → 日常交付，产出 §2 要求的反馈；
- 实施 B0（观察工具化），由实现方按本规划派发；
- 反馈达到 §2 门槛后，回到本文档定型 D1–D4，进入正式设计评审链
  （设计 → ADR → 计划 → 实现 → 独立审阅）。
